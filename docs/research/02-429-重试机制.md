# 429 Too Many Requests 重试机制

## 背景

Codex 通过 `config.toml` 中的 `[model_providers.custom]` 配置自定义 API 供应商，其直连方式下重试行为由 Codex 客户端控制：

- `request_max_retries`：HTTP 请求最大重试次数（默认 4，当前配置 4）
- `stream_max_retries`：流式断线重连次数（默认 5，当前配置 5）
- `stream_idle_timeout_ms`：流式空闲超时（默认 300000ms）
- `websocket_connect_timeout_ms`：WebSocket 连接超时（默认 15000ms）

**没有重试间隔配置项。** 重试的基础延迟 `base_delay` 在源码中硬编码为 200ms，采用指数退避（200ms → 400ms → 800ms → ...），无法通过 `config.toml` 修改。

## 问题

上游 API 返回 HTTP 429 Too Many Requests 时，Codex 客户端默认**不重试**（`retry_429 = false`），直接报错给用户。

## 方案：通过协议代理层处理 429

CodexPlusPlus 的 `protocol_proxy` 运行在 `127.0.0.1:57321`，作为 Codex 与上游 API 之间的中间层：

```
Codex  →  localhost:57321 (protocol_proxy)  →  上游 API
```

在这个路径上，代理层可以拦截上游返回的 429，自行等待后重试，对 Codex 透明。

### 实现位置

`crates/codex-plus-core/src/protocol_proxy.rs`

### 实现思路

在代理层转发上游 HTTP 请求并读取响应时，检查 HTTP 状态码：

1. 如果上游返回 429，不立刻透传错误给 Codex
2. 按自定义策略等待后重试（支持指数退避 + 抖动）
3. 重试成功后将响应正常返回给 Codex
4. 达到重试上限后仍未成功，再将 429 透传给 Codex

### 可配置参数（建议）

| 参数 | 说明 | 建议默认值 |
|------|------|-----------|
| 最大重试次数 | 429 后最多重试几次 | 3 |
| 基础延迟 | 首次重试前的等待时间 | 1000ms |
| 退避因子 | 指数退避的倍数 | 2.0 |
| 最大延迟 | 重试等待的上限 | 10000ms |
| 抖动比例 | 避免惊群效应的随机范围 | 0.1 |

### 对比直连

| 特性 | 直连 | 代理层处理 |
|------|------|-----------|
| 429 发生后 | 报错给用户 | 静默重试，对 Codex 透明 |
| 重试间隔 | 不可配置，硬编码 200ms | 可自定义，支持指数退避 |
| 控制粒度 | 仅次数 | 次数、间隔、退避因子全可控 |
| 实现复杂度 | 无 | 需在代理层加重试逻辑 |

## 相关文件

- `crates/codex-plus-core/src/protocol_proxy.rs` — 协议代理主要实现
- `crates/codex-plus-core/src/settings.rs` — 配置定义（可在此处添加重试参数）
- `~/.codex/config.toml` — Codex 全局配置，`base_url` 指向 protocol_proxy
