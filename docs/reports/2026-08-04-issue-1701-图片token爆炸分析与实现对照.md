## 一、结论速览

1. 帖主的现象描述和根因方向是**成立**的：`view_image` 等工具把图片以 base64/data URL 形式放进工具输出，Codex++ 在部分路径上把它当文本字符串透传，确实会以文本 token 计费并撑爆上下文。
2. 帖主预期“图片应该走图片 token”只对**支持图片输入的上游**成立；对 DeepSeek 这类纯文本模型，上游根本没有图片 token，正确目标是“**不要让 base64 以文本形式进入上游**”，即剥离、占位，或用 VLM 转成文字描述。
3. issue 评论区给出的方向（把 `function_call_output.output` / tool 消息 content 里的 data URL 纳入 Strip/VLM）**是正确解法**。本分支 PR #1550 的 R4 修复已经实现了这条主线。
4. 当前实现**尚未合入 main**，所以 1.2.43/1.2.44 用户仍然会遇到 #1701、#1761 这类问题；且 R4 仍有边缘缺口：Responses 协议下数组形式的 `output`、VLM 配置缺失时的降级、溢出估算不识别字符串 base64。
5. 社区还提出了可借鉴的替代方案：图片路径占位（PR #1750）、per-model 能力开关、上下文 catalog 修正（PR #1722）、fail-open/fail-close 取舍讨论等。

## 二、Issue #1701 原文与评论

### 2.1 帖主反馈

- 现象：上传图片后，Codex 调用 `view_image` 查看图片，产生大量 token。
- 实测：一张 639k 图片消耗约 664,694 token；一张 90k 图片消耗约 90,070 token。
- 判断：base64 编码后的图片信息跟随上下文走了文本 token 通道。
- 预期：图片信息应该走图片 token。
- 版本：Codex++ 1.2.43，Windows。

这个现象是可信的。base64 会把文件膨胀约 4/3，再叠加 JSON 序列化和 tokenizer 碎片化，几百 KB 图片变成几十万 token 完全合理。

### 2.2 评论区根因定位

评论区的共识：

- 图片不是作为用户消息里的 `image_url` / `input_image` 块进入上下文，而是作为 `function_call_output` 的工具输出返回。
- Responses → Chat Completions 转换中，`response_output_text()` 会把数组形式的 `output` 用 `canonical_json_string()` 整体序列化成字符串，于是 base64 变成了普通文本。
- 原有 `strip_images_only()` / `collect_recent_image_messages()` 只遍历 `messages[].content`，且 `collect_recent_image_messages()` 只看 `role == "user"`，所以工具输出里的 base64 原样透传。
- 实测诊断显示：`vlm_context_overflow` 分支大量触发，但 `skipped_images: 0`，说明图片不是以图片块存在，而是藏在字符串里，剥离函数删不到。

## 三、帖主说法是否在理

### 3.1 在理的部分

- “base64 图片被当成文本 token 计算”是真实存在的协议处理盲区。
- “调用 `view_image` 后上下文爆炸”与 #1405 只解决了用户消息图片、没有解决工具输出图片的事实一致。
- 实测 token 数字与该机制吻合。

### 3.2 需要修正的部分

- “图片应该走图片 token”不是普适预期。Codex++ 接入的上游如果是纯文本模型，API 不提供图片 token，只能：
  - 多模态上游：保留 `input_image` / `image_url` 块，交给上游按图片 token 处理；
  - 纯文本上游：剥离成占位符，或先调 VLM 转成文字描述再发给主模型。
- 因此 #1701 的正确验收标准不应是“把 base64 变成图片 token”，而是“**base64 永远不能以文本形式进入纯文本上游**”。

## 四、本分支已经做到的实现

### 4.1 按模型粒度上下文窗口（main 已合入，当前分支包含）

- PR [#1197](https://github.com/BigPizzaV3/CodexPlusPlus/pull/1197) 已合入 main：
  - `model_windows` / 模型列表窗口列，废弃模型名后缀写法；
  - 自动生成 `model_catalog_json` 并写入 config.toml；
  - 支持每模型 `context_window`、`effective_context_window_percent`、`auto_compact_token_limit` 等。
- 当前分支基于包含该实现的最新 main，所以“按模型粒度配置上下文窗口与自动压缩阈值”的主体已存在。
- 已知未闭合问题：PR [#1722](https://github.com/BigPizzaV3/CodexPlusPlus/pull/1722) 指出无后缀自定义模型即使配置了窗口也可能不生成 catalog，仍回落 258K。

### 4.2 图片处理管线（本分支增量）

当前 `vision-enhancement` 分支在 main（#1405）基础上新增：

- `extract_data_urls()`：扫描字符串中的 `data:image/...;base64,...`，返回位置与 URL；
- `strip_data_urls_in_messages()`：Strip 模式下把 tool/`function_call_output` 消息里的 data URL 替换为 `[图片已省略]`；
- `analyze_data_urls_in_messages()`：VLM 模式下把 data URL 交给 VLM 转文字描述，成功后替换为 `[图片描述] ...`，失败则替换为失败占位符，base64 不再保留；
- `protocol_proxy.rs` 接入点：Strip 分支和 VLM 分支都在处理完消息图片块后，再处理工具输出里的 data URL。

## 五、他提出的方法能解决目的吗？当前实现做到多少

### 5.1 方法有效性

评论区建议的“扫描 tool 消息 output/content 字符串中的 base64 data URL，纳入 Strip/VLM”方向正确：

- 能直接消灭“base64 以文本进入纯文本上游”的核心问题；
- 能复用现有 per-model 三态（SendAsIs / Strip / VLM）；
- 不需要改 Codex Desktop 客户端。

### 5.2 当前实现覆盖矩阵

| 场景 | 当前分支是否覆盖 | 说明 |
|---|---|---|
| Chat Completions 协议，工具输出被序列化为字符串 content | ✅ | R4 的 `strip_data_urls_in_messages` / `analyze_data_urls_in_messages` 可处理 |
| Responses 协议，`function_call_output.output` 为字符串 | ✅ | 遍历 `output` 字段字符串 |
| Responses 协议，`function_call_output.output` 为数组（含 `input_image` 块） | ❌ | 两个函数都只处理 `Value::String`；`strip_all_images` 也只处理 `content` 数组 |
| `custom_tool_call_output` 为字符串 | ✅ | 转换后作为 tool 消息 content 字符串处理 |
| `custom_tool_call_output` 为数组 | ❌ | 同上，数组块未进入图片管线 |
| VLM 配置完整且 VLM 成功 | ✅ | 图片被转成文字描述 |
| VLM 调用失败 | ✅（fail-open） | base64 被替换为失败占位符，不再透传 |
| VLM 配置缺失/不完整 | ❌ | VLM 分支直接跳过，字符串 base64 仍可能透传 |
| SendAsIs 模式 | 设计如此 | 多模态上游保留原始图片块，符合预期 |
| 上下文溢出保护对字符串 base64 的估算 | ⚠️ | `estimate_tokens` 会把字符串 base64 当文本计入，且剥离函数看不到字符串；R4 在协议层后处理能删除它，但预算/截断逻辑没有把它当图片处理 |
| 发布版本 | ❌ | R4 未合入 main，1.2.43/1.2.44 没有该修复 |

结论：**核心链路已经做到，但没有做到 100%**。常见 `view_image` 在 Chat 协议下（输出被序列化为字符串）的问题已被 R4 堵住；仍缺 Responses 数组输出、VLM 配置缺失降级、以及把字符串 base64 纳入溢出预算这三条保底线。

## 六、该方法优缺点

### 6.1 优点

- 针对性极强：直接命中 `view_image` 工具输出 base64 文本化的真实路径。
- 改动集中在代理层，不依赖 Codex 客户端升级。
- 与现有 per-model 三态设计天然兼容：纯文本模型 Strip/VLM，多模态模型 SendAsIs。
- VLM 成功后主模型只收到文字描述，上下文占用大幅下降。
- 有测试覆盖：R4 新增 11 个测试，当前分支 vision 90 个、protocol_proxy 57 个测试通过。

### 6.2 缺点与风险

- **协议结构脆弱**：只处理字符串形式的 `output`/`content`，数组形式的 Responses 输出会漏。
- **字符串扫描依赖格式**：data URL 的序列化方式一旦变化（转义、JSON 包装、非 base64 字符）就可能漏检。
- **没有真正实现“图片 token”**：对纯文本上游只能降级为描述/占位，无法保留像素细节。
- **VLM 配置缺失时仍可能透传**：分支代码在 VLM 配置不完整时直接跳过整个 VLM 分支，没有按 Strip 降级。
- **溢出估算盲区**：`vlm_context_overflow` 分支计算纯文本 token 时会把字符串 base64 当普通文本，`skipped_images` 数不到它；R4 的后处理能删，但预算语义仍不正确。
- **fail-open 的幻觉风险**：VLM 失败后只给模型一个失败占位符，主流模型一般会如实说明，但小模型仍有编造可能；社区维护者 `kanchengw` 在 #1550 评论中明确建议 fail-closed 更稳。
- **描述信息损失**：VLM 描述不可能是原图无损替代，用户追问细节时可能答不出。

### 7.3 值得借鉴的社区做法

1. **图片路径占位（#1750）**：把图片落盘并给模型绝对路径，让模型通过 MCP 读图工具自行查看。适合“模型具备读图 MCP 但上游不支持图片输入”的场景；需要额外处理临时文件生命周期和路径安全。
2. **能力声明（#1191/#574）**：per-model 标记是否支持图片输入，而不是全局剥图。当前 `textOnly` checkbox 就是该思路。
3. **fail-closed（#1550 评论）**：VLM 未配置/失败时直接报错比静默 fail-open 更保险，至少应在配置缺失时按 Strip 降级而不是透传。
4. **完整 catalog 而非单模型 catalog（#1261 维护者意见）**：catalog 生成必须保留模型列表完整性。
5. **用户配置指引（#1594 评论）**：`model_context_window` 是全局覆盖，不是 fallback；按模型窗口配置时应留空全局窗口。这个认知应写进文档和 UI 提示。

## 八、对当前分支的后续建议

按优先级整理：

1. **补齐 Responses 数组输出路径**：让 `function_call_output.output` / `custom_tool_call_output.output` 里的 `input_image` 数组块也进入 send-as-is / strip / VLM 管线，而不是只处理字符串。
2. **协议转换层按元素处理**：在 `responses_to_chat_completions` 中把 output 数组里的图片块保留为 `image_url` 块、文本块提取为字符串，避免先整体序列化成 JSON 字符串。
3. **VLM 配置缺失按 Strip 降级**：VLM 模式但配置不完整时，至少执行 `strip_data_urls_in_messages`，不能直接跳过。
4. **溢出预算纳入字符串 data URL**：`vlm_context_overflow` 分支计算 `text_only_estimated_tokens` / `skipped_images` 时识别字符串 base64，或先统一做字符串剥离再估算。
5. **为 #1701/#1761 补端到端测试**：覆盖 Chat 字符串、Responses 字符串、Responses 数组、`custom_tool_call_output`、VLM 配置缺失、溢出分支六类场景。
6. **合入 PR #1550 后再关闭 #1701/#1761**：当前修复只存在于分支，不能只靠 issue 评论宣称已解决。
7. **合入 PR #1722**：修复无后缀自定义模型 catalog 不生成的问题，让 per-model 上下文窗口真正闭环。
8. **可选评估 #1750 路径占位模式**：作为 Strip 的增强，给有读图 MCP 的模型保留本地看图能力。
9. **fail-open/fail-close 给用户可选**：VLM 失败时至少要有明确状态注入；若维护者倾向 fail-closed，可做成配置项。
10. **文档更新**：修正 `docs/research/01-调研结果.md` 中把 `model_context_window` 描述成“回退默认”的说法，实际是“全局覆盖”。
